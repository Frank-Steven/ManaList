> 状态：v1.2（2026-11-08）
> 定位：本文档是「助理」域的统领性说明——明确助理是什么、能做什么、不能做什么，以及各机制的去处。

## 1. 定位

助理是 ManaList 三主 Tab（库 / 任务 / 助理）之一，是用户操作应用的**对话式入口**：

- 用户用自然语言表达意图（整理收件箱、安排日程、记笔记、建立关联……）；
- AI **不直接写数据**，而是把意图拆成**原子工具调用**，每个调用生成一条**变更提案**；
- 所有写入提案进**待确认区**，由**人工审批**后才执行生效。

一句话：**助理提案，人做决定。**

## 2. 两条硬约束（不可妥协）

1. **原子化**：一个工具调用 = 一个最小变更（建一个任务、改一个字段、插一个锚点）。无批量/复合工具；复合意图由 AI 拆成多个提案。
2. **全量审批**：AI 不产生任何静默写入。写工具产出永远先落 `change_proposals`（pending），人工通过后执行；只读工具（查询/检索）直接执行并回注对话。唯一的效率优化是「默认勾选」（如垃圾标记提案），「通过」动作仍须人触发。

### 2.1 原子变更的 CRDT 语义

原子化不只是颗粒度要求，它让每条提案天然具有 **CRDT 式的独立可拆分性**：

- **独立**：每条提案自含完整参数（payload），不依赖同批其他提案的执行结果；任何一条都可单独通过/拒绝/重试，状态机互不牵连。
- **可拆分**：一个复合意图拆出的 N 条提案，可以按任意子集、任意顺序审批；部分通过、部分拒绝是合法常态，不需要「整批要么全过要么全滚」的事务包装。
- **可交换、可重复**：同一批次内的提案彼此无顺序依赖（交换律）；执行按目标 id 二次校验且幂等（重复执行不产生二次效果，幂等律）。审批执行失败置 `failed` 可重试，不污染其他提案。

**冲突收敛机制（v1.2 修订）**：多助理并行、人机并发、选择性审批三类并发真实存在，「单设备 + 人工审批串行落库」不再被视为充分条件。数据层引入真正的 CRDT——LWW-Register（字段级）、OR-Set（锚点集合）、追加集（笔记正文）+ op log（事实源/撤销/审计），提案审批时做「直接生效 / 自动 rebase / superseded」三态裁决，人的修改在决胜序上永远不被助理静默覆盖。完整设计见 `docs/crdt.md`。原子化作为工具设计纪律的要求不变：这条调用能否独立于其他任何调用被单独通过、单独撤销？做不到，说明它不够原子，继续拆。

## 3. 运行模式

Assistant 的运行可分解为五个正交部分，各自独立演进：

| 部分 | 职责 | 关键性质 |
|---|---|---|
| 对话管理 | 多对话（类 Agent）：独立上下文、独立模型配置；多对话回合并行，同对话新回合取消旧回合 | 回合服务自持（`AssistantTurnHandle`），离开页面不死 |
| 上下文组装 | 历史消息 + 附件正文内联（`[#note:标题]` 引用头）+ 工具说明书（`tool_spec.dart` 单一事实源） | 附件即库资源的只读投影，见 §6 |
| 模型通道 | LinkModel 在线走本地模型（adb 通道），否则走对话绑定的远程端点；SSE 流式 | 桌面端只透传，不解析不执行 |
| 工具解析与提案 | 流式解析 ```tool 块 → 校验 → 落 `change_proposals`（pending） | 容错解析、按 `(chat_message_id, block_index)` 幂等去重 |
| 审批与执行 | 待确认区人工审批 → 执行 payload → 结果回注对话 → 进撤销队列 | 权限边界在执行层再强制一次（双保险） |

UI 形态（对话列表 / 对话页 / 待确认区 / 附件选择 / 模型选择）见 `docs/ui-structure.md` §6.3，实现位于 `mobile/lib/ui/assistant/`。

## 4. 能力边界：工具清单

助理能做的事**恰好等于**这张表（首版），此外无其他写入通道：

| 工具 | 类型 | 说明 |
|---|---|---|
| `task.create` / `task.update` / `task.delete` | 写 | 任务的增、改（单任务粒度）、删；**已归档任务不可改/删** |
| `task.list` / `task.search` | 只读 | 查询任务 |
| `note.create` / `note.append` | 写 | 新建笔记、章节末尾追加（`note.replace_section` 已随锚点简化废弃，见 `anchors-v2.md` §4） |
| `note.read` | 只读 | 读取笔记 |
| `anchor.create` / `anchor.remove` | 写 | 在库中基本对象（消息条 / 笔记章节 / 文件）与任务之间建立/移除对象级锚点（只落表、不动正文，双向跳转，见 `anchors-v2.md`） |
| `library.search` | 只读 | 检索库（笔记/消息/文件的标题与正文） |
| `message.set_priority` | 写 | 标记一条消息的优先级（一条消息一个提案） |
| `inbox.triage` | 提案生成器（只读执行） | 批量评估指定范围消息：本地垃圾规则预过滤 + 分批子调用模型；产出全部是一组原子提案（`message.set_priority` / `task.create`），进待确认区 |

权限边界（执行层强制，与校验双保险）：

- 不可修改/删除已归档任务；
- 首版不提供笔记/文件的删除工具；
- 不可触碰配对、密钥、设置。

工具协议与解析细节（围栏块语法、流式状态机、容错、幂等去重）：`design-v3-details.md` §2。

## 5. 执行链路

```
模型输出（```tool 块）
  → tool_parser        流式解析（容错；未闭合块随流中断丢弃）
  → proposal_service   校验（目标存在性、字段）→ 落 change_proposals(pending)，对话内出现提案卡片
  → 待确认区           人工逐条/批量审批（任意子集、任意顺序，见 §2.1）
  → proposal_executor  通过后执行 payload（幂等；权限边界再查一次）→ applied / failed
  → 回注               执行结果作为 tool 消息写回原对话，保持上下文连贯
  → 撤销队列           applied 变更进 UndoService，提供事后反悔通道
```

代码集中在 `mobile/lib/services/assistant/`；桌面端 LinkModel 只做 SSE 透传，**不解析、不执行**工具（提案的生成与执行都在手机端）。

## 6. Assistant 与库的联系

助理与库（笔记 / 消息 / 文件）的联系分三类，合起来构成助理的全部输入与输出面：

### 6.1 获取信息（库 → 助理）

- **附件**：对话可挂载库中任意笔记/消息/文件，请求时展开为带引用头的上下文块；vision 模型可接收图片附件（base64 内联）。
- **检索**：`library.search` 让 AI 按关键词自主发现库内容，不必依赖用户手动挂附件。
- **任务查询**：`task.list` / `task.search` 同理覆盖任务域。
- 附件是库资源的**只读引用**：对话只持 `{type, id}`（§7.2），发送时展开为上下文副本供模型阅读，不构成新本体、不回写（SSA，见 §7.1）。

### 6.2 操作库资源（助理 → 库，经审批）

- 笔记：新建、章节末尾追加（`note.create/append`）；
- 消息：优先级标记（`message.set_priority`）；消息正文只读（v1.2 起锚点不再写入正文，受限写入通道取消）；
- 文件：首版只读（作为附件与锚点目标），不提供写入/删除工具。

所有写入一律走「提案 → 待确认区 → 人工审批」，与用户手动操作落到**同一张表、同一套服务**——AI 没有旁路通道。

### 6.3 关联待办（库 ↔ 任务：锚点）

- 具体方案见「锚点 v2」设计（`docs/anchors-v2.md`，v1.2 起取代行内 marker 方案）：锚点是库中基本对象（消息条 / 笔记章节 / 文件）与任务之间的**对象级关联**，只落 `task_anchors` 表、正文不写入任何 marker；一个锚点连一个任务，一个任务可被多个锚点连接，双向跳转。
- AI 通过 `anchor.create` / `anchor.remove` 建立与移除关联（同样走审批）；并发增删的冲突语义为 OR-Set（`docs/crdt.md` §4.3）。
- **功能对等原则**：人工（用户手动）关联任务的方式目前尚不完整（v1.2 起人工入口为对象详情页「关联任务」区 + 列表多选批量关联，`anchors-v2.md` §3），但**人工路径必须与 Assistant 保持至少同等的功能覆盖**——AI 能做的关联操作，用户不借助对话也必须能做。锚点服务（`AnchorService`）是两侧唯一的实现落点，AI 工具与人工 UI 都只是它的调用方，保证行为一致、无能力差。

## 7. 数据一致性原则

### 7.1 SSA（Static Single Assignment，静态单赋值）

库内的归档与删除操作，**无论由用户还是 Agent 发起**，都遵守 SSA 原则：

- **内容本体只赋值一次**：笔记正文、消息正文、文件本体等资源一旦写入即为不可变值，永不原地修改。「修改」的语义是**产生一个新本体（新 id）并让引用切换到新 id**，旧本体不动——变量可以重新指向，值本身不被改写。
- **归档/删除是引用与元数据层面的操作**：它们只翻转状态位或解除引用，不触碰本体；恢复/撤销因此是低成本的引用操作，而不是数据重建。
- **Agent 无特权也无例外**：Agent 的写操作与人工操作走同一服务层、同一语义，差异只在发起入口（提案审批流 vs 直接 UI 操作）；已归档实体对 Agent 关闭写权限（§4 权限边界），归档线是 Agent 不可逾越的边界。
- SSA 与 §2.1 的原子性互相成就：本体不可变，提案的「目标」在审批期间不会被原地篡改，执行前的二次校验才有意义；提案失败/撤销也只是引用切换，不留半成品状态。

### 7.2 以 id 共享资源本体

SSA 的不可变本体配合**不同 id 共享同一本体**的策略，节省存储与性能消耗：

- 文件本体在 `attachment_store` 只存一份，库内所有引用（笔记 attachments、`file://` 正文引用、对话附件、锚点 target）都只用 **id** 指向它，不复制内容；内容相同的本体可经哈希去重，多个 id 指向同一物理存储（SSA 的不可变性使这种共享天然安全——没有写入方，就没有共享冲突）；
- 锚点行只存对象与任务的 id 引用，任务标题展示时联查——任务改名，所有锚点展示自动跟随，零改写；
- 对话附件同样只存 `{type, id}`，发送时才展开为上下文；删除本体前的引用检查即基于这些 id 关系，引用归零才回收物理存储。

### 7.3 模型（数据模型）绝对稳定

- 数据模型（表结构、锚点语义、存档格式）是系统的地基，**保持绝对稳定**：新需求优先用既有模型表达，不做破坏性 schema 变更；
- 演进只允许增量（加列、加表、加工具），并配套迁移测试与存档格式版本号；
- 工具协议可以迭代（提示词、解析容错），但**落库语义不变**——这是「提案可跨版本重放、存档可往返」的前提。

## 8. 与其他域的关系

- **库**：见 §6（获取信息 / 操作资源 / 关联待办）；消息的通知采集与助理无关，照常进行。
- **任务**：任务是助理的主要产出；锚点让任务与库内容双向关联，AI 与用户共享同一 `AnchorService`（§6.3）。
- **设置**：AI/模型配置只存在于助理域（模型选择器），设置页不出现。
- **待确认区与对话松耦合**：删除对话不删提案；审批后的变更走全局撤销队列。

## 9. 模型路由

1. 手机探测到电脑端 LinkModel 在线（USB adb 通道，自动配对零配置）→ 用电脑端本地模型；
2. 否则 → 用当前对话绑定的远程 OpenAI 兼容端点（用户在模型选择器中自配）；
3. 目标模型声明 `vision` 时，图片附件内联 base64 随请求发送；非 vision 模型一律不附带图像。

## 10. 明确不做的事

- 不做任何静默写入、不做「自动通过」开关；
- 不做复合/批量写工具（批量意图 = 多个原子提案）；冲突收敛由 `docs/crdt.md` 的 CRDT 机制承载（v1.2 起取代「不引入 CRDT」的旧决策），但仍不做多设备副本同步；
- 不做笔记/文件删除、不碰已归档任务、不碰设置与密钥；
- 不做资源本体的复制/第二副本（一切引用走 id，见 §7.2）；
- 桌面端不做业务逻辑（无解析、无执行、无 dashboard）；
- v2 的批处理评估管线已废弃，其能力仅以 `inbox.triage` 工具形态存在。
